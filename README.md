## 📖 About the Project

The **OSS Club Website** is the central digital hub for the **Open Source Software Club** at **Sai Vidya Institute of Technology (SVIT)**, Rajanukunte, Bengaluru. Designed and built entirely by student developers, the platform showcases club activities, technical projects, upcoming workshops, hackathons, open-source resources, and contributor achievements.

The repository represents our commitment to modern web development standards, inclusive open-source practices, and peer-to-peer technical mentorship.

### 🎯 Mission & Vision

- **Learn in Public:** Demystify Git, version control, and collaborative software engineering for students at every stage of their academic journey.
- **Ship Real Software:** Transition from toy academic projects to production-grade software that solves community and institutional challenges.
- **Foster Community:** Create a welcoming, harassment-free environment where curious beginners and experienced hackers build together.
- **Connect with Global Open Source:** Bridge campus talent with major global initiatives like Google Summer of Code (GSoC), Hacktoberfest, LFX Mentorship, and Outreachy.

---

## ✨ Key Features

- **🏠 Dynamic Homepage:** Interactive hero section, real-time club statistics, marquee of active open-source projects, and upcoming event highlights.
- **📅 Events & Workshops Management:** Filterable catalog of tech talks, hands-on workshops, bootcamps, and hackathons with RSVP and calendar integration.
- **🚀 Project Showcase:** Curated gallery of student-led open-source repositories featuring tech stack tags, live demo links, and GitHub star counts.
- **👥 Contributor Hall of Fame:** Automated leaderboard recognizing open-source contributions, pull requests, and club event volunteers via GitHub API integration.
- **📚 Learning Resources & Blog:** Markdown/MDX-powered technical guides on Linux, Git, web development, containerization, and open-source contribution roadmaps.
- **🎨 Modern, Accessible UI:** Built with Tailwind CSS and Radix UI primitives (shadcn/ui), featuring seamless light/dark mode theming and full WCAG accessibility compliance.
- **⚡ High Performance & SEO:** Server Components via Next.js App Router, dynamic metadata, OpenGraph cards, and sub-second page loads.

## 🛠️ Tech Stack

### Core Framework & Language
- **[Next.js 14+](https://nextjs.org/)** — Full-stack React framework utilizing the App Router, React Server Components (RSC), and Server Actions.
- **[React 18+](https://react.dev/)** — UI library for composable component architecture.
- **[TypeScript 5+](https://www.typescriptlang.org/)** — Strict type safety, interface validation, and improved developer experience.

### Styling & Component Library
- **[Tailwind CSS 3.4+](https://tailwindcss.com/)** — Utility-first CSS framework for responsive and maintainable styling.
- **[shadcn/ui](https://ui.shadcn.com/)** — Accessible, customizable component primitives built on top of [Radix UI](https://www.radix-ui.com/).
- **[Lucide Icons](https://lucide.dev/)** — Consistent, lightweight icon set.
- **[next-themes](https://github.com/pacocoursey/next-themes)** — Seamless dark and light mode switching without layout flash.

### Database & Backend
- **[Supabase](https://supabase.com/)** — Open-source Firebase alternative powered by PostgreSQL, providing authentication, relational data storage, and Row Level Security (RLS).
- **PostgreSQL** — Relational database engine for event registrations, project metadata, and user profiles.

### Tooling, Quality & Deployment
- **[pnpm](https://pnpm.io/)** — Fast, disk-space efficient package manager.
- **[ESLint](https://eslint.org/)** & **[Prettier](https://prettier.io/)** — Automated code quality and opinionated formatting.
- **[Vercel](https://vercel.com/)** — Edge deployment platform with continuous integration and branch preview environments.

## 📋 Prerequisites

Before running the project locally, verify that your development environment meets the following requirements:

- **Node.js**: `v18.17.0` or higher (LTS recommended, e.g., `v20.x`). Check with `node -v`.
- **pnpm**: `v8.0.0` or higher. Check with `pnpm -v`. If not installed, run:
  ```bash
  corepack enable
  corepack prepare pnpm@latest --activate
  ```
- **Git**: `v2.30.0` or higher. Check with `git --version`.
- **Supabase Account / CLI** (Optional for local development; a shared development instance or mock is available for club contributors).

## 🚀 Quick Start

Follow these steps to set up the project locally on your machine:

### 1. Clone the Repository

```bash
git clone https://github.com/Open-Source-Software-Club/OSS_website.git
cd OSS_website
```

### 2. Install Dependencies

> [!IMPORTANT]
> Always use **pnpm** to install dependencies. Avoid using `npm` or `yarn` directly, as this will generate conflicting lockfiles and break CI checks.

```bash
pnpm install
```

### 3. Configure Environment Variables

Create a local environment file by copying the example template:

```bash
cp .env.example .env.local
```

Open `.env.local` in your editor and configure the necessary keys (see [Environment Variables](#-environment-variables) below for details). For local UI development, default placeholder values will allow the website to boot.

### 4. Run the Development Server

```bash
pnpm dev
```

Open [http://localhost:3000](http://localhost:3000) with your browser to view the application. Hot reloading is enabled; edits in `src/app/` will reflect immediately.

## 🔐 Environment Variables

The following environment variables are required or optional depending on your local development scope. Add them to your `.env.local` file:

| Variable Name | Description | Required? | Default / Example Value |
|:---|:---|:---:|:---|
| `NEXT_PUBLIC_SITE_URL` | Base canonical URL of the deployed application | **Yes** | `http://localhost:3000` |
| `NEXT_PUBLIC_SUPABASE_URL` | Public API URL of your Supabase project instance | **Yes** | `https://[PLACEHOLDER-PROJECT-ID].supabase.co` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Public anonymous API key for Supabase client | **Yes** | `eyJhbGciOiJIUzI1NiIsInR5cCI...` |
| `SUPABASE_SERVICE_ROLE_KEY` | Elevated key for administrative backend Server Actions | *No (Admin only)* | `[PLACEHOLDER_SERVICE_ROLE_SECRET]` |
| `NEXT_PUBLIC_GITHUB_ORG` | GitHub organization name for API sync | *Optional* | `Open-Source-Software-Club` |
| `GITHUB_ACCESS_TOKEN` | GitHub Personal Access Token to avoid API rate limits | *Optional* | `ghp_[PLACEHOLDER_TOKEN]` |
| `NEXT_PUBLIC_GA_MEASUREMENT_ID` | Google Analytics 4 Measurement ID | *Optional* | `G-[PLACEHOLDER]` |

> [!CAUTION]
> Never commit `.env.local`, production secrets, or private API keys to GitHub. Our repository enforces strict `.gitignore` rules and automated secret scanning.

## 🚦 Continuous Integration & Deployment

Every pull request passes through a quality gate before it can reach `main`.
The full design is documented in **[docs/CI_CD.md](docs/CI_CD.md)**; this is the
summary.

### Required checks

| Check | Guarantees |
|:---|:---|
| **Repository Hygiene** | no forbidden files, no oversized files, valid YAML, valid `CODEOWNERS` |
| **PR Conventions** | Conventional Commit title, valid branch name, reviewable size, linear history (re-runs when you edit the title) |
| **Verify** | ESLint · TypeScript · Prettier · Vitest · `next build` |
| **Secret Scan** | no credential material in any tracked file, no private keys |
| **Dependency Review** | no new moderate-or-higher vulnerability, no disallowed licence |

### What is blocked, mechanically

| Never commit | Enforced by |
|:---|:---|
| `.env`, `*.pem`, `*.key`, private keys | `check-forbidden-files.sh`, `check-secrets.sh` |
| `package-lock.json`, `yarn.lock`, `.npmrc` | `check-lockfiles.sh` |
| `node_modules/`, `.next/`, `dist/`, `coverage/` | `check-forbidden-files.sh` |
| `.DS_Store`, `Thumbs.db`, `*.swp`, `.idea/` | `check-forbidden-files.sh` |
| Files larger than 1 MiB | `check-large-files.sh` |
| Trailing whitespace, tabs, CRLF, missing final newline | `check-text-hygiene.sh` |
| Non-Conventional-Commit messages | `check-commit-msg.sh`, `check-pr-meta.sh` |
| Merge commits, force-pushes and direct pushes to `main` | `Protect main` ruleset |
| Changes to `release/**`, `hotfix/**`, `support/**` without review | `Protect release branches` ruleset |
| Deleting or moving a `v*` release tag, non-semver tag names | `Protect release tags` ruleset |
| Branch names that do not follow `<type>/<description>` | `Branch naming` ruleset |
| Unreviewed changes to `supabase/migrations`, `lib/github`, `lib/rbac` | `.github/CODEOWNERS` |

The rulesets live in `.github/branch-protection/rulesets/` and are applied with
`bash .github/branch-protection/apply.sh`. They are validated in CI by
`check-rulesets.sh`, so a required status check that names a job no workflow
emits fails the build instead of silently making a branch unmergeable.

### Run the same gate locally

```bash
git config core.hooksPath .githooks   # once per clone (or: ./scripts/install-hooks.sh)
./scripts/checks/run-all.sh           # run everything, on demand
```

The hooks call the **same scripts** as CI, so what is blocked locally is exactly
what is blocked in the cloud.

### Deployment

**Vercel** handles deployment natively — a Preview per pull request, Production
on `main`. GitHub Actions is the quality gate, not the deployer. Production
database migrations are the one exception: they run through
`.github/workflows/db-migrate.yml` behind manual approval, never automatically
from a pull request.
